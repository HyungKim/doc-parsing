# PDF/PPTX 텍스트 추출 (좌표 규칙 방식)

PDF와 PPTX에서 글을 사람이 읽는 순서대로 뽑고, 매 쪽 반복되는 문구를 빼고, 쪽 제목을 따로 뽑습니다.
처리 전(before)과 처리 후(after)를 나란히 보여 주는 HTML 리포트를 만듭니다.

- 글자의 좌표와 크기, 그려진 선만으로 판단합니다(재귀 X-Y cut). AI 모델은 쓰지 않습니다.
- PDF는 pdfplumber로, PPTX는 python-pptx로 읽습니다.
- 실행 중 인터넷에 접속하지 않습니다.

4.0부터 **2단계(1차 걸러내기 모델 비교)** 가 붙었습니다. 뽑은 덩어리와 줄 가운데 특허출원 검토가 필요한 것을 걸러 내는 모델 네 가지를 회사 PC에서 돌려 비교합니다.
1단계(추출)는 그대로이고, 결과도 그대로 나옵니다. 2단계는 따로 설치해야 하며 설치하지 않아도 1단계는 전과 같이 씁니다. → [2단계: 1차 걸러내기 모델 비교](#2단계-1차-걸러내기-모델-비교)

## 설치와 실행 (Windows, 배치파일)

1. 이 폴더를 통째로 PC에 둡니다.
2. `install.bat`을 더블클릭합니다. 이 폴더 안에 전용 가상 환경(`.venv`)을 만들고 라이브러리 두 개(pdfplumber, python-pptx)와 그에 딸린 것들을 설치합니다. 모두 합쳐 100MB 안팎입니다.
3. `run.bat`을 더블클릭해 경로를 입력하거나, 자료를 `run.bat` 위로 끌어다 놓습니다. 폴더 하나, 파일 하나, 파일이나 폴더 여러 개 모두 됩니다. 수십 개가 넘으면 한 폴더에 모아 폴더를 놓으세요(한 번에 넘길 수 있는 경로 길이에 한도가 있습니다).
   끝나면 `out\index.html`이 브라우저로 열립니다.

Python 3.9 이상이 필요합니다. Python이 없으면 먼저 설치하되, 설치 화면에서 "Add python.exe to PATH"를 체크하세요.

### 인터넷이 막힌 PC에 설치하기

1. 인터넷이 되는 Windows PC에서 `download_wheels.bat`을 실행합니다. `wheels` 폴더에 설치 파일이 모입니다.
   두 PC의 Python 버전이 같아야 합니다(예: 둘 다 3.11).
2. 폴더 전체를 `wheels` 폴더와 함께 회사 PC로 옮긴 뒤 `install.bat`을 실행합니다.
   `wheels` 폴더가 있으면 인터넷 없이 그 안의 파일로 설치합니다.
   이전 버전에서 만들어 둔 `wheels` 폴더도 그대로 쓸 수 있습니다(필요한 파일이 이미 들어 있고, 남는 파일은 설치되지 않습니다).

## 직접 명령으로 실행하기

```bat
py -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python compare.py 자료폴더 -o out
```

- 폴더 안의 `.pdf`, `.pptx`를 모두 처리하고 `out\index.html`을 만듭니다.
- 이름이 같은 PPTX와 PDF(예: `보고.pptx`, `보고.pdf`)를 함께 넣으면 두 결과가 얼마나 같은지 비교하는
  `보고.pptx-vs-pdf.html`도 만듭니다.
- `samples` 폴더의 샘플로 먼저 시험해 볼 수 있습니다: `run.bat samples`

### 옵션

| 옵션 | 뜻 |
|---|---|
| `--keywords "사내한,Draft"` | 항상 제거할 문구 추가 (기본: Confidential, 대외비, 사외비, Internal Use Only 등) |
| `--repeat-ratio 0.6` | 본문 한가운데의 글을 반복 문구로 볼 쪽 비율. 낮추면 더 많이 지움 |
| `--include-hidden` | PPTX의 숨긴 슬라이드도 포함 |
| `--no-images` | 리포트에 쪽 그림을 넣지 않음 (파일이 작아짐) |
| `--min-chars 5` | 띄어쓰기를 포함해 이 글자 수 이하인 줄을 출력에서 뺌. `0`이면 빼지 않음 |
| `--keep-non-korean` | 한글이 없는 줄도 출력에 남김 |

## 리포트 보는 법

- **Before 열**: 아무 처리 없이 읽은 원문. 번호 하나가 라이브러리가 따로 꺼낸 단위(PDF는 줄, PPTX는 도형)이고, 쪽 그림의 회색 상자가 그 위치입니다. 빨강 취소선은 제거된 문구, 초록은 제목으로 뽑힌 줄.
- **After 열**: 좌표 규칙을 적용한 결과. 쪽 그림 위의 번호가 읽는 순서, 초록 상자가 제목. 아래에 제목, 본문, 제거한 문구와 이유.
- **표**: 표로 인식한 덩어리는 왼쪽에 파란 줄이 붙고, 같은 표를 두 가지 모양으로 보여 줍니다(아래 "표를 글로 바꾸는 두 가지 모양").
  풀어 쓴 표는 표의 한 행이 한 문장이고, 문장마다 초록 번호가 붙습니다. 번호는 리포트에서 문장을 구분해 보여 주는 표시이고 뽑은 글에는 들어가지 않습니다.
  리포트 위쪽의 "표가 있는 쪽" 목록으로 표가 있는 쪽을 바로 찾을 수 있고, `표: 칸 구분`, `표: 풀어 쓰기` 체크로 한쪽 모양만 볼 수 있습니다.
- **표 위에 얹힌 글**(PDF): 표 영역 안에 있지만 표의 글이 아니라고 판단해 떼어 낸 덩어리에는 갈색 꼬리표가 붙습니다.
  리포트 위쪽의 "표 위에 얹힌 글을 떼어 낸 쪽" 목록으로 바로 찾을 수 있습니다(아래 "표 위에 얹힌 글").
- **PPTX ↔ PDF 일치율**(같은 이름의 PPTX와 PDF를 함께 넣었을 때): 쪽의 글을 한 줄로 이어 붙여 글자와 순서가 얼마나 같은지 본 값입니다. 띄어쓰기, 줄바꿈, 덩어리를 끊은 위치는 세지 않습니다.
- 위쪽 체크 상자로 열을 숨기거나 쪽 그림을 끌 수 있습니다.
- `*.json`에는 같은 결과가 자료로 들어 있습니다. 결과는 `methods` → `A` → `pages` 아래에 쪽마다 `title`, `body`, `removed`로 들어 있습니다(2.3까지는 PDF의 이름이 `A-mu`, `A-pl`이었습니다).
  `body_flat`은 본문에서 표만 풀어 쓴 모양으로 바꾼 것이고, `tables`에는 표마다 두 모양의 글과 칸 구조(합친 칸 포함)가 들어 있습니다.
  `tables`의 `flat_lines`는 풀어 쓴 글을 문장마다 나눈 목록이고, `over_table`은 그 쪽에서 표 위에 얹힌 글로 보고 떼어 낸 글의 목록입니다.

## 출력에서 빼는 줄

다음 모델에 넣을 글에서 뜻이 부족한 줄을 뺍니다. 3.5부터 기본으로 적용됩니다.

| 빼는 줄 | 예 |
|---|---|
| 한글이 하나도 없는 줄 | `6000`, `2025`, `Strictly Confidential`, `ABC Corp.` |
| 띄어쓰기를 포함해 5자 이하인 줄 | `성장 지역`, `핵심 사업`, `2026년`, `A사` |

- 줄 단위로 판단합니다(문단 합치기와 색·크기 나누기를 마친 뒤의 한 줄). 한 덩어리의 줄이 모두 빠지면 그 덩어리도 없어지고, 번호는 남은 덩어리끼리 다시 매깁니다.
- **제목은 빼지 않습니다.** 짧은 제목이 많기 때문입니다.
- **표 안의 줄은 빼지 않습니다.** 행을 빼면 표가 깨지기 때문입니다. 한글이 전혀 없는 표만 통째로 뺍니다.
- 뺀 줄은 버리지 않고 남깁니다.
  - 리포트의 After 열 아래 "제거한 문구"에 내용과 이유(`한글이 없는 줄`, `5자 이하의 짧은 줄`)가 나옵니다.
  - 배치 그림의 빨간 점선 상자가 그 글이 있던 자리입니다. 마우스를 올리면 내용이 나오고, 위쪽 "제거한 자리" 체크로 끌 수 있습니다.
  - 리포트 위쪽에 이유별 개수와 "한글이 없거나 짧아서 줄을 뺀 쪽" 바로가기가 있습니다.
  - `이름.json`의 쪽마다 `removed`(문구와 이유), `이름.units.json`의 `removed`(쪽, 문구, 이유)에 들어 있습니다.
- 끄려면 `python compare.py 자료폴더 --min-chars 0 --keep-non-korean`. 글자 수 기준만 바꾸려면 `--min-chars 3`처럼 줍니다.

## 색과 크기가 다른 글을 다른 줄로

본문 옆에 다른 색, 다른 크기로 코멘트나 부연 설명을 붙여 둔 경우, 그대로 두면 서로 다른 내용이 한 줄에 섞입니다.
3.4부터는 한 줄 안에서 **글자색과 크기가 모두 다른** 조각을 다른 줄로 나눕니다(`docparse/stylesplit.py`). PDF와 PPTX에 같은 기준을 씁니다.

| 경우 | 3.3까지 | 3.4 |
|---|---|---|
| 옆에 따로 붙인 코멘트 (PDF) | `추진 일정※ 3월 이사회에서 확정 예정` | `추진 일정` / `※ 3월 이사회에서 확정 예정` |
| 뒤에 붙은 작은 회색 설명 | `영업이익 230억 원 (전년 대비 30억 원 감소)` | `영업이익 230억 원` / `(전년 대비 30억 원 감소)` |
| 앞에 붙은 작은 빨간 꼬리표 | `[검토 중] 신규 거점 설립 계획` | `[검토 중]` / `신규 거점 설립 계획` |

- 덩어리(번호)는 그대로이고 그 안에서 줄만 나뉩니다. 읽는 순서와 배치 그림은 달라지지 않습니다.
- 다음은 나누지 않습니다.
  - 색만 다르거나 크기만 다른 경우
  - 문장 가운데에 끼어 있는 조각(양옆 글의 모양이 같음). 강조한 숫자나 주석 번호가 여기에 해당합니다
  - 보이는 글자가 4자 미만인 조각
- 리포트 위쪽 표의 "색·크기로 나눈 줄"과 "색·크기로 줄을 나눈 쪽" 목록으로 나눈 곳을 찾을 수 있습니다. JSON에는 쪽마다 `style_breaks`(나눈 횟수)가 있습니다.
- PPTX에서 색을 따로 정하지 않은 글은 검정 계열의 기본 글자색으로 봅니다. 기본 글자색이 흰색인 어두운 서식에서는 일부 나누지 못할 수 있습니다.
- Python 3.9에 설치되는 구버전 pdfminer.six는 Mac(Quartz)에서 만든 PDF의 빨강·노랑 계열 글자색을 검정에 가깝게 읽어, 그런 PDF에서는 일부가 나뉘지 않습니다.
  색을 RGB로 직접 지정한 PDF(Windows에서 만든 PDF의 방식)는 Python 3.9와 3.12에서 같은 결과가 나오는 것을 확인했습니다.

## 다음 모델에 넣는 단위

뽑은 글을 분류기 같은 다음 모델에 넣을 때, 한 번에 얼마만큼을 입력 하나로 넣을지 고를 수 있도록 세 가지 단위로 나눈 파일을 함께 만듭니다.

| 파일 | 내용 |
|---|---|
| `이름.pdf.json` (기존) | 쪽마다 `title` 하나와 `body` 하나. `body`는 덩어리와 줄이 모두 줄바꿈 글자로 이어진 글 하나라서, 어디까지가 한 덩어리인지는 알 수 없습니다 |
| `이름.pdf.units.json` | 같은 글을 `units.page`(쪽 통째), `units.block`(덩어리 하나씩), `units.line`(줄 하나씩) 세 목록으로 나눈 것. 목록의 항목 하나가 입력 하나입니다 |
| `이름.pdf.units.html` | 지금의 실제 출력과 세 단위를 쪽마다 나란히 보여 주는 화면. `index.html`의 "입력 단위" 열과 리포트 위쪽에 링크가 있습니다 |

- **쪽 통째**: 제목과 본문 전체가 입력 하나. 쪽(슬라이드) 자체를 분류할 때 맞습니다.
- **덩어리**: 리포트에서 번호 하나로 보이는 글상자·문단 묶음·표가 입력 하나. 소제목과 그 아래 글이 따로 떨어진 글상자면 서로 다른 입력이 됩니다.
- **줄**: 덩어리 안의 한 줄(문단 하나, 표라면 한 행)이 입력 하나. 마침표로 자른 문장이 아니어서 한 줄에 문장이 여러 개일 수 있습니다.
- 항목마다 `id`(예: `p4-b3-l2` = 4쪽 3번 덩어리 2번째 줄), `page`, `block`, `kind`(title, text, table), 그 쪽의 `title`, `text`가 들어 있습니다. 제목도 항목 하나로 들어갑니다(`kind`가 `title`).
- 표는 값마다 머리글을 붙여 풀어 쓴 모양으로 넣습니다(한 줄만 떼어 놓아도 뜻이 남도록). 풀어 쓰지 못한 표는 칸 구분 모양이고, `table_form`으로 구분됩니다. 덩어리 항목에는 칸 구분 모양도 `text_pipe`로 들어 있습니다.
- 비교 화면의 노랑은 10자 이하의 짧은 입력입니다. 소제목처럼 혼자서는 뜻이 부족한 입력이 얼마나 생기는지 단위별로 볼 수 있습니다(`summary`에 개수가 있습니다).
- 세 목록이 담는 글은 같고 나누는 자리만 다릅니다. 제거한 반복 문구는 어느 단위에도 들어가지 않습니다.

## 표를 글로 바꾸는 두 가지 모양

| 모양 | 예 | 특징 |
|---|---|---|
| 칸 구분 (기존, `body`) | `설비 투자 \| 120억 원 \| 150억 원` | 짧다. 빈 칸은 건너뛰어서, 빈 칸이 있거나 머리글이 여러 단이면 어느 열의 값인지 알 수 없다 |
| 풀어 쓰기 (`body_flat`) | `국내 > 제조 > 설비 투자 — 2026년 상반기 계획: 101, 2026년 상반기 실적: 102` | 값마다 행 머리글과 열 머리글이 붙는다. 검색이나 AI 입력처럼 글이 조각나도 뜻이 남아야 할 때 맞다. 글은 2배 안팎으로 길어진다 |

풀어 쓰기는 칸을 합친 모양에서 머리글이 어디까지인지 추정합니다(`docparse/tables.py`).

- 표의 한 행이 한 문장(한 줄)이 됩니다. 값이 있는 행이 5개인 표는 문장 5개로 나옵니다. 표 제목과 구분 줄도 따로 한 줄입니다.
- 머리글이 여러 단이면 위에서 아래로, 왼쪽에서 오른쪽으로 이어 붙입니다. 단 수에는 제한이 없습니다.
- 맨 왼쪽 열들(행 머리글)에서 세로로 합친 칸이 시작하는 줄부터는 본문으로 봅니다. 옆으로 합친 머리글 아래에 하위 머리글 줄이 없는 표에서 첫 본문 줄이 머리글로 들어가지 않게 하기 위해서입니다.
- 표 전체 폭의 맨 윗줄은 `[표] 제목`으로, 본문 가운데의 전체 폭 줄은 구분 줄로 보고 아래 행들의 머리글 앞에 붙입니다.
- 행 머리글의 빈 칸은 같은 묶음 안에서 위 칸을 이어받습니다.
- 머리글이 분명하지 않으면(열 머리글이 없는 표 등) 풀어 쓰지 않고 칸 구분 모양으로 두되, 빈 칸과 합친 칸의 자리를 채워 열을 맞춥니다. 리포트에 그 이유가 표시됩니다.
- PPTX는 칸 합치기 정보가 파일에 있어 정확합니다. PDF는 표의 선에서 칸을 되살리므로, 표로 인식되지 않은 표(세로선이 없는 표 등)는 풀어 쓸 수 없습니다.
  그런 표는 표가 아닌 보통 글로 나옵니다.
- **양옆이 트인 표**(PDF): 선이 사방으로 닫힌 곳만 칸이 되므로, 바깥 세로선이 없고 칸에 바탕색도 없는 표는 맨 왼쪽 열과 맨 오른쪽 열의 글이 표에서 빠집니다.
  3.2부터는 가로선 여러 개가 같은 자리에서 끝나고 그 안쪽에 세로선이 있으면, 끝자리에 세로선이 있는 것으로 쳐서 그 열도 표에 넣습니다(`docparse/pdf_plumber.py`의 `open_side_lines`).
  세로선이 하나도 없는 표는 여전히 표로 찾지 못합니다.

## 표 위에 얹힌 글

발표 자료에서는 표 위에 다른 색 글상자로 코멘트를 올려 두는 일이 많습니다. PDF에는 "이 글자는 표의 것"이라는 표시가 없어서,
위치만 보면 그 코멘트가 칸 경계에서 잘려 칸마다 원래 글 뒤에 붙습니다(`80억 원 ※ 2027년 전망은 | 95억 원 잠정치이며 …`).
3.1부터는 이런 글을 표에서 떼어 내 표 다음에 따로 적습니다(`docparse/pdf_common.py`의 `find_overlays`). PPTX는 코멘트가 별도 도형이라 원래 섞이지 않습니다.

가려내는 단서는 두 가지입니다.

- **저장 순서**: 표는 자기 글을 첫 칸부터 마지막 칸까지 차례로 저장합니다. 그 앞이나 뒤에, 이미 지나간 칸 자리로 되돌아와 저장된 글은 다른 도형의 글입니다.
- **칸 경계**: 표의 글은 칸 안에 머뭅니다. 빈틈 없이 이어진 글이 칸 경계나 표 가장자리를 넘으면 표의 글이 아닙니다.

순서가 어긋난 글이라도, 경계를 넘었거나 표의 글이 이미 있는 칸에 다른 색이나 크기로 덧찍힌 경우에만 떼어 냅니다.
글자색만으로는 판단하지 않습니다(표 안에도 빨간 음수 같은 색 글자가 흔합니다).

코멘트가 테두리나 바탕이 있는 상자에 들어 있으면, 그 상자의 선이 표의 선과 만나 칸을 더 잘게 쪼갭니다.
3.2부터는 떼어 낸 글을 감싼 상자를 찾아 그 상자를 빼고 표를 다시 찾으므로 칸 구조가 원래대로 나옵니다(`overlay_boxes`).

가려내지 못하는 경우:

- 표의 맨 마지막 칸 안에만 들어간 코멘트(저장 순서가 어긋나지 않음)
- 칸의 글과 색, 크기가 같은 코멘트가 한 칸 안에 있는 경우
- 빈 칸 하나 안에 들어간 코멘트는 그 칸의 글로 남습니다
- 칸 순서대로 저장하지 않는 PDF에서는 저장 순서로 판단하지 않아 3.0과 같은 결과가 나옵니다

`samples/table_comments.pptx`와 `.pdf`가 이 경우들을 모은 샘플입니다(슬라이드 제목이 경우 이름).
샘플의 PDF는 Mac의 PowerPoint로 만든 것입니다. **Windows PowerPoint도 같은 순서로 저장하는지는 확인하지 못했으므로**,
회사 PC의 PowerPoint로 `table_comments.pptx`를 같은 이름의 PDF로 저장해 `samples` 폴더에 덮어쓴 뒤 `run.bat samples`로 돌려 보면 바로 확인할 수 있습니다.
1~5쪽, 8~11쪽에 갈색 꼬리표가 붙고 `table_comments`의 PPTX ↔ PDF 일치율이 98% 안팎이면 같은 순서입니다.

## 읽는 순서 기준값 시험

읽는 순서를 정할 때 쓰는 기준값(예: 좌우로 자르려면 여백이 6pt 이상)은 샘플로 정한 값입니다.
실제 자료에서도 안전한지 확인하려면 자료를 `tune.bat` 위로 끌어다 놓습니다(직접 실행: `python tune.py 자료폴더`).

- 자료를 읽는 방법은 `run.bat`과 같습니다(PDF는 pdfplumber, PPTX는 python-pptx).
- 기준값을 하나씩 바꿔 가며 순서를 다시 정하고, 지금 값일 때와 순서가 달라지는 쪽을 세어 `out\tune.html`로 보여 줍니다.
- 바로 옆 값으로 바꿔도 순서가 같으면 지금 값이 그 자료에서 안전한 것입니다.
- 바로 옆 값에서 달라지는 쪽은 지금 값일 때와 바꾼 값일 때를 쪽 그림으로 나란히 보여 줍니다.
  - 그림 위의 번호가 읽는 순서이고, 순서가 달라진 덩어리는 주황색입니다.
  - 쪽을 자른 자리가 선으로 그려집니다. 두 그림에 똑같이 있는 자름은 회색 점선, 한쪽에만 있는 자름은 빨간 선이고 빨간 띠가 그때 쓴 여백, 숫자가 그 너비입니다.
  - ①은 두 결과가 처음 갈라지는 곳이고, 그림 위 문장이 그곳의 여백 크기와 두 값이 각각 어떻게 했는지를 적어 줍니다.
    (예: "가장 넓은 여백은 좌우 7pt, 위아래 20pt. 좌우로 자르려면 지금은 6pt, 바꾼 값에서는 8pt 이상이어야 합니다.")
  - 빨간 점선 상자는 그 영역을 더 자르지 않고 한 번에 순서를 정한 곳입니다(격자로 보았거나 자를 여백이 없음).
  - PPTX는 쪽 그림이 없어 상자와 선만 그립니다. 쪽 그림을 빼려면 `python tune.py 자료폴더 --no-images`.
- 먼저 `run.bat`으로 같은 자료를 돌려 두면, 쪽 이름을 눌러 비교 리포트의 그 쪽으로 갈 수 있습니다.
- 기준값 자체는 `docparse/layout.py` 맨 위에 있습니다. 이 시험은 값을 바꿔 저장하지 않습니다.

## 2단계: 1차 걸러내기 모델 비교

1단계가 뽑은 덩어리와 줄마다 "특허출원 검토가 필요한 글인가"를 0~1 점수로 매기고, 모델 네 가지의 결과를 나란히 비교합니다.
빠르게 걸러 내는 것이 목적이라 글을 지어내는 모델(생성형)은 쓰지 않습니다. 모두 PC 안에서 CPU로 돌고, 실행 중 자료가 밖으로 나가지 않습니다.

| 이름 (`--models`에 쓰는 이름) | 종류 | 크기 | 라이선스 |
|---|---|---|---|
| bge-m3 (`bge-m3`) | 임베딩 + 분류기 | 약 2.3GB | MIT |
| KURE-v1 (`kure-v1`) | 임베딩 + 분류기. bge-m3를 한국어로 더 학습한 것 | 약 2.3GB | MIT |
| multilingual-e5-small (`me5-small`) | 임베딩 + 분류기. 작고 빠름 | 약 0.5GB | MIT |
| bge-m3-zeroshot-v2.0-c (`bge-m3-zeroshot`) | 문장 판별. 정답으로 학습시키지 않음 | 약 1.1GB | MIT |

- **임베딩 + 분류기**: 모델이 글을 숫자 묶음으로 바꾸고, 그 숫자 묶음으로 판단합니다. 정답이 없을 때는 기준 문장과 얼마나 비슷한지로 판단하고(학습 전), 정답이 모이면 작은 분류기를 학습시켜 판단합니다(학습 후).
- **문장 판별**: 글과 기준 문장을 함께 넣어 "이 문장이 이 글에 대해 맞는가"를 모델이 직접 따집니다. 기준 문장 수만큼 모델을 돌리므로 가장 느립니다.

### 설치

1. `install.bat`을 실행해 둔 폴더에서 `install_screen.bat`을 더블클릭합니다.
   라이브러리(torch, transformers, sentence-transformers, scikit-learn) 1.5GB 안팎과 모델 파일 약 6GB를 **이 폴더 안에** 받습니다. 폴더가 있는 드라이브에 8GB 이상 여유가 필요합니다.
   설치 중 임시 파일과 모델 라이브러리의 보관 폴더도 이 폴더 안으로 돌려 두어 C: 드라이브에 쌓이지 않게 했습니다.
2. 모델은 `models` 폴더에 들어갑니다. 중간에 끊기면 다시 실행해 못 받은 것만 이어서 받습니다.

인터넷이 막혔거나 모델을 받는 곳(huggingface.co)이 막힌 PC라면, 인터넷이 되는 Windows PC(같은 Python 버전)에서 `download_screen.bat`을 실행합니다.
만들어진 `wheels` 폴더와 `models` 폴더를 회사 PC의 이 폴더에 넣고 `install.bat`, `install_screen.bat`을 차례로 실행하면 됩니다.

### 쓰는 순서

1. **`screen.bat`** 을 더블클릭합니다. `out` 폴더에 있는 추출 결과 전체에 네 모델로 점수를 매기고 `out\screen\index.html`을 엽니다.
   자료를 `screen.bat` 위로 끌어다 놓으면 추출(`run.bat`과 같은 일)부터 이어서 합니다.
   이때는 정답이 없으므로 **학습 전**(기준 문장만으로 매긴) 점수만 나옵니다.
2. **`label.bat`** 을 더블클릭하면 정답 붙이는 화면이 브라우저에 열립니다. 줄마다 **예**(검토 필요) 또는 **아니오**를 누릅니다. 누를 때마다 저장됩니다.
3. 그 화면의 **학습하고 결과 보기**를 누르면(또는 `screen.bat`을 다시 실행하면) 정답으로 분류기를 학습시키고 비교 화면을 새로 만듭니다.
   '예'와 '아니오'가 각각 4개 이상이면 학습합니다. 한 번 계산한 글은 다시 계산하지 않으므로 두 번째부터는 몇 초면 끝납니다.

`samples\tech_review.pptx`는 기술 아이디어와 일정·예산 같은 글을 섞어 지어낸 샘플입니다. `screen.bat samples`로 먼저 시험해 볼 수 있습니다.

### 기준 문장 (학습 전 판단에 쓰는 문장)

정답 없이 판단할 때 쓰는 문장은 `screen_sentences.txt`에 있습니다(처음 실행할 때 기본 문장으로 만들어집니다).

```
+ 이 글은 새로운 기술적 구조, 장치, 방법 또는 알고리즘을 제안하거나 설명한다.
+ 이 글은 기존 기술의 문제를 해결하는 기술적 수단과 그 효과를 설명한다.
+ 이 글은 제품이나 공정의 성능을 높이는 새로운 설계나 기술 아이디어를 설명한다.
- 이 글은 일정, 조직, 인력, 비용, 매출 같은 일반적인 업무 현황을 설명한다.
- 이 글은 시장 동향이나 경쟁사 현황 같은 사업 환경을 설명한다.
- 이 글은 목차, 출처, 인사말처럼 구체적인 기술 내용이 없다.
```

- `+` 줄은 검토가 **필요한** 글을 나타내는 문장, `-` 줄은 **필요 없는** 글을 나타내는 문장입니다. 몇 개든 됩니다(각각 하나 이상).
- 글마다 이 문장들 가운데 어느 문장에 가장 가까운지를 따져, `+` 문장 쪽으로 기운 정도를 0~1 점수로 냅니다.
- **고치는 방법**: `label.bat` 화면의 "기준 문장 보기·고치기"를 펼쳐 고치고 저장하거나, 파일을 메모장으로 고칩니다. 그다음 다시 계산하면 반영됩니다.
- 기본 문장은 회사 자료를 보지 못한 채 제가 짐작해 적은 것입니다. 회사에서 실제로 검토 대상이 되는 내용에 맞게 고쳐 쓰세요.
- 비교 화면의 기준 문장 표에는 문장마다 "그 문장에 가장 가까웠던 덩어리 수"가 모델별로 나옵니다. 한 번도 뽑히지 않는 문장은 하는 일이 없는 문장입니다.
- 문장을 고치면 고치기 전의 점수를 따로 남겨 두고, 비교 화면에 **고치기 전 → 지금**의 수치 변화를 보여 줍니다(아래 "개선 정도" 참고).
- 문장을 바꾸면 바뀐 문장만큼 모델을 다시 돌립니다. 문장 판별 모델은 글 수만큼 다시 돌려야 해서 가장 오래 걸립니다.

### 쪽 제목 반영 (옵션, 기본은 꺼짐)

쪽 제목을 보고 그 쪽에 있는 덩어리와 줄의 점수를 올리거나 내리는 기능입니다. **기본은 꺼져 있고**, 꺼져 있으면 점수와 화면이 이 기능이 없을 때와 똑같습니다.

```
최종 점수 = (1 − 비율) × 글 점수 + 비율 × 제목 점수
```

- 제목 점수는 제목을 글 하나로 보고 기준 문장으로 매긴 점수입니다(학습 전 점수와 같은 방법). 비율이 0.3이면 글 70%, 제목 30%입니다. 제목이 없는 쪽은 글 점수 그대로입니다.
- **켜는 방법**: `label.bat` 화면의 "쪽 제목 반영"에서 비율을 적고 저장하거나, `screen_options.txt`의 `title_weight` 값을 메모장으로 고칩니다(0 ~ 0.9, 0이 꺼짐). 그다음 다시 계산하면 반영됩니다. 글은 다시 계산하지 않으므로 금방 끝납니다.
- 켜면 비교 화면의 모든 점수와 수치가 제목을 반영한 값이 되고, **쪽 제목을 반영한 효과** 부분이 생깁니다.
  - **반영 전 → 후**: 글 점수만일 때와 제목을 섞었을 때를 같은 정답으로 짝지어 비교한 개선 정도(순위 정확도 변화와 범위, 통과 비율 변화). 학습 전 점수와 학습 후 점수 각각에 대해 나옵니다.
  - **비율을 바꿨을 때**: 비율 0, 0.1, …, 0.5에서의 수치를 나란히 보여 줍니다. 어느 비율이 좋은지, 켜는 것이 나은지를 여기서 고릅니다.
  - **제목마다의 점수**: 어떤 제목이 기술적이라고 판단됐는지 볼 수 있습니다.
- 문서별 화면에는 쪽마다 제목 점수가 나오고, 칸에 마우스를 올리면 섞기 전의 글 점수가 나옵니다. "제목 반영으로 판단이 바뀐 것"만 골라 볼 수 있습니다.
- 주의할 점
  - 같은 쪽의 글이 함께 오르내립니다. 기술적인 제목 아래의 일정 줄도 올라가고, "개발 일정" 같은 제목의 쪽에 섞인 기술 내용은 내려갑니다(놓칠 위험). 비율을 크게 잡지 않는 편이 안전합니다.
  - "추진 현황"처럼 두루뭉술한 제목은 점수가 중간쯤 나와 효과가 없습니다.
  - 학습 후에도 제목 점수는 기준 문장으로 매긴 값을 씁니다. 학습시킨 분류기로 제목에 점수를 매기는 것도 해 봤으나, 문장으로 학습한 분류기는 짧은 제목에 점수를 낮게 주어 글 점수를 모두 끌어내렸습니다.
  - "기준 문장을 고친 효과"는 제목 반영과 섞이지 않게 언제나 글 점수로만 잽니다.

### 정답 붙이기

- 정답은 **줄 단위**로 붙입니다. 덩어리의 정답은 줄에서 따옵니다: 줄 하나라도 '예'면 덩어리도 '예', 모든 줄이 '아니오'면 덩어리도 '아니오', 그 밖에는 아직 모름.
  그래서 한 번 붙인 정답으로 덩어리 단위와 줄 단위를 모두 잴 수 있습니다.
- 같은 글은 어느 문서에 있든 한 번만 붙이면 됩니다(글 내용으로 기억합니다). 추출을 다시 해도 정답은 유지됩니다.
- 키보드: `↑` `↓` 이동, `Y` 예, `N` 아니오(누르면 다음 줄로), `X` 지우기, `A` 그 덩어리의 남은 줄 모두 아니오.
- 한 번 계산한 뒤에는 "점수 높은 순", "헷갈리는 순"으로 늘어놓을 수 있습니다. '예'가 드문 자료에서 '예'를 빨리 찾는 데 씁니다.
  다만 수치를 공정하게 재려면 점수 높은 것만 골라 붙이지 말고 **한 쪽이나 한 문서를 통째로** 붙이는 것이 좋습니다.
- 정답은 `labels\labels.json`에 저장됩니다. 이 화면은 이 PC 안에서만 열립니다(주소 127.0.0.1). `label.bat` 창을 닫으면 끝납니다.

### 비교 화면 읽는 법

`out\screen\index.html` 한 화면에 기준 문장, 모델, 학습 전·후 수치, 덩어리 대 줄 비교, 문서 목록이 있습니다. 문서 이름을 누르면 덩어리마다 줄마다의 점수가 나옵니다.

**넣는 크기 세 가지** (덩어리로 넣을지 줄로 넣을지 비교)

| 보는 방식 | 뜻 |
|---|---|
| 덩어리로 넣음 | 덩어리의 글 전체를 한 번에 모델에 넣어 점수를 매김 |
| 줄로 넣어 덩어리로 합침 | 줄마다 따로 넣어 점수를 매기고, 그 가운데 가장 높은 점수를 덩어리의 점수로 삼음 |
| 줄로 넣음 | 줄마다 따로 넣고 줄 단위로 맞았는지 잼 |

앞의 둘은 둘 다 덩어리 단위로 맞았는지를 재므로 **서로 바로 비교할 수 있습니다**. 어느 크기로 넣는 것이 나은지는 이 둘을 보면 됩니다.
문서별 화면에서 "덩어리로 넣을 때와 줄로 넣을 때 판단이 다른 것"을 체크하면 판단이 갈린 덩어리만 볼 수 있습니다.

**수치**

- **순위 정확도**: 정답이 '예'인 글을 '아니오'인 글보다 높은 점수로 줄 세운 정도. 1이면 완벽, 0.5면 무작위입니다. 문턱값을 어디에 두느냐와 상관없어 모델끼리 비교하기 좋습니다.
- **찾아낸 비율**: 정답이 '예'인 것 가운데 통과시킨 비율. 걸러내기에서는 놓치지 않는 것이 중요하므로 이 값이 높아야 합니다.
- **통과 비율**: 전체 글 가운데 다음 단계로 넘기는 비율. 같은 만큼 찾아낸다면 낮을수록 잘 걸러 낸 것입니다.
- **90% 찾는 문턱에서의 통과 비율**: '예'의 90% 이상을 놓치지 않도록 문턱을 맞췄을 때 넘어가는 양. "놓치지 않으면서 얼마나 줄여 주는가"를 한 숫자로 봅니다. 90%는 `--recall`로 바꿉니다.
- 학습 후 수치는 **그 글을 빼고 학습시킨 분류기**가 매긴 점수로 잽니다(최대 다섯 묶음으로 나눠 돌아가며 시험. 될 수 있으면 같은 쪽의 글은 같은 묶음에 둡니다). 자기가 본 정답을 맞히는 것으로 점수가 부풀지 않게 하기 위해서입니다.

**개선 정도** (전과 후를 수치로 비교)

같은 글에 매긴 "전" 점수와 "후" 점수를 짝지어 두 가지로 잽니다.

1. **순위 정확도 변화와 그 범위**: 후 − 전. 괄호 안은 정답이 붙은 글을 다시 뽑기를 1,000번 되풀이했을 때 그 차이가 놓이는 범위(95%)입니다.
   범위 전체가 0보다 크면 **나아짐**, 전체가 0보다 작으면 **나빠짐**, 0을 걸치면 **우연일 수 있음**으로 적습니다. 정답을 더 붙이면 범위가 좁아집니다.
2. **통과 비율 변화**: '예'의 90%를 찾도록 문턱을 맞췄을 때 다음 단계로 넘기는 양이 몇 %p 줄었는지.

이 비교는 두 군데에 나옵니다.

- **학습 전 → 학습 후**: 정답으로 분류기를 학습시킨 효과. 맨 위에 점 두 개(빈 점이 학습 전, 찬 점이 학습 후)를 선으로 이은 그림으로도 보여 줍니다.
- **기준 문장 고치기 전 → 지금**: 기준 문장을 고친 효과. 같은 정답으로 비교합니다.

### 결과 파일

```
out/screen/index.html            비교 화면
out/screen/이름.screen.html      문서별: 덩어리와 줄마다 네 모델의 점수 (학습 전 → 후)
out/screen/scores.json           글마다의 점수와 수치 (다음 단계나 다른 분석에 쓸 수 있음)
out/screen/cache/                한 번 계산한 결과 (지우면 처음부터 다시 계산)
labels/labels.json               붙인 정답
labels/classifiers/모델__단위.json   학습시킨 분류기의 계수
models/                          모델 파일
screen_sentences.txt             기준 문장
screen_options.txt               설정 (쪽 제목을 반영하는 비율)
```

`scores.json`의 `scores`는 언제나 글 점수입니다. 쪽 제목 반영을 켜면 제목 점수(`title_scores`)와 섞은 점수(`final`)가 함께 적힙니다.

`out` 폴더의 1단계 결과(`이름.html`, `이름.json`, `이름.units.json` 등)는 2단계가 건드리지 않습니다. 2단계를 한 번 돌린 뒤 `run.bat`을 다시 실행하면 `out\index.html`에 2단계 화면으로 가는 길이 하나 생깁니다.

### 직접 명령과 옵션

```bat
python screen.py out                       계산하고 비교 화면 만들기
python screen.py out --models me5-small    고른 모델만
python screen.py --download                모델 파일만 받기
python label.py out                        정답 붙이는 화면
```

| 옵션 | 뜻 |
|---|---|
| `--models 이름,이름` | 돌릴 모델만 고름 |
| `--recall 0.9` | 놓치지 않으려는 '예'의 비율 |
| `--max-len 512` | 모델에 넣는 글의 최대 길이(토큰). 넘는 부분은 잘림 |
| `--sentences 파일` | 기준 문장 파일 |
| `--labels 파일` | 정답 파일 |
| `--models-dir 폴더` | 모델 파일을 두는 폴더 |
| `--no-download` | 모델 파일이 없어도 내려받지 않음 |
| `--title-weight 0.3` | 쪽 제목 점수를 섞는 비율. 주지 않으면 설정 파일의 값(처음에는 0 = 반영 안 함) |
| `--options 파일` | 설정 파일 |

### 알아 둘 점

- **회사 PC(Windows)에서는 아직 돌려 보지 못했습니다.** Mac에서 Python 3.12와 3.9 두 환경으로 확인했습니다. 실제 회사 자료로도 확인하지 못했습니다.
- 시험에 쓴 자료는 지어낸 샘플이라 너무 쉽습니다(거의 모든 조합이 순위 정확도 1에 가깝게 나옵니다). **어느 모델과 어느 크기가 나은지는 회사 자료에 정답을 붙여서 봐야 압니다.**
- 속도는 PC마다 다릅니다. 실행 창에 "1초에 몇 개"가 나오니 그것으로 가늠하세요. Mac에서는 bge-m3와 KURE-v1이 1초에 20~40개, multilingual-e5-small이 200~400개, 문장 판별 모델이 1초에 30~45쌍(기준 문장 6개면 글 5~7개)이었습니다. 회사 PC에서는 이보다 느릴 것으로 봅니다.
- 쪽 제목은 걸러낼 대상에 넣지 않았습니다(덩어리의 문맥으로만 둡니다). 표는 덩어리 하나로, 표의 행은 줄 하나로 다룹니다.
- 정답이 적을 때는 수치가 크게 흔들립니다. 수치 옆의 정답 수와 개선 정도의 범위를 함께 보세요.
- 문장 판별 모델은 정답으로 학습시키지 않으므로 "학습 후"가 없습니다. 정답이 쌓일수록 임베딩 + 분류기 쪽만 나아집니다.

## 알려진 한계

- **차트**: PDF에는 축 숫자와 값 레이블이 글자로 찍히지만 PPTX에서는 차트 제목·계열·항목만 읽습니다.
- **PDF의 줄바꿈**: PDF에는 문단 표시가 없어 자동 줄바꿈과 문단 끝을 좌표로 추정합니다.
  띄어쓰기 자리에서 줄이 넘어간 경우 띄어쓰기가 빠질 수 있습니다("계약을체결함").
  PDF를 만든 프로그램에 따라 정도가 다르므로 회사 자료로 꼭 확인하세요.
- **표**: 기본 모양(`body`)은 칸을 ` | `로 이어 한 행을 한 줄로 적고 빈 칸은 건너뜁니다. 풀어 쓴 모양은 머리글 추정이 틀리면 값에 엉뚱한 머리글이 붙을 수 있으니 리포트에서 두 모양을 비교해 확인하세요. 여러 쪽에 걸쳐 이어지는 표는 쪽마다 따로 처리합니다.
- **표 위에 얹힌 글**: 위 "표 위에 얹힌 글"의 가려내지 못하는 경우 참고. 표가 아닌 글 위에 얹힌 코멘트는 다루지 않습니다.
- **세로쓰기**: 표의 칸에 세로쓰기로 두 줄 이상 적힌 글(PDF)은 글자 순서가 섞일 수 있습니다. 한 줄짜리 세로쓰기는 괜찮습니다.
- **쪽 바깥의 글**: pdfplumber는 쪽 바깥에 놓여 화면에 보이지 않는 글도 읽어 줍니다. 이 프로그램은 그 글을 따로 걸러 내지 않습니다.
- **구형 .ppt, 스캔 PDF**는 지원하지 않습니다(.ppt는 .pptx로 저장 후 사용).
- 발표자 노트는 읽지 않습니다(PDF에 없는 내용).
